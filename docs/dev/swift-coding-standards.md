# Swift 编码规范

## 基本原则

- 优先可读性、正确性和局部一致性。
- 采用 Swift API Design Guidelines；类型名使用名词，行为使用清晰动词。
- 避免 `Manager`、`Helper`、`Utils` 等模糊命名，名称应体现具体职责。
- 使用 `let` 表达不变性，用具名常量代替缺少语义的魔法值。
- `guard` 处理前置条件和提前返回，复杂条件提取为具名变量。
- 集合无结果时返回空集合，除非 `nil` 本身具有独立业务含义。

## 类型与状态

- 优先 `struct` 和不可变值；需要身份或共享可变状态时再使用 class/actor。
- 互斥状态用关联值枚举表达。
- 新的 observable state 优先使用 Observation。
- ViewModel 更新 UI 状态时标注 `@MainActor`。
- 依赖通过初始化器注入；单例只用于确有进程级唯一性的能力。

## 并发

- 优先 `async/await` 与结构化并发。
- 不用无所有者的 fire-and-forget `Task` 隐藏生命周期问题。
- 支持取消，并在昂贵步骤或循环中检查取消状态。
- actor 内的状态跨 `await` 可能变化；恢复后重新验证相关前置条件。
- 不用 `@unchecked Sendable` 掩盖未经证明的线程安全。
- UI 生命周期异步工作优先使用 `.task`。

## SwiftUI

- View 描述 UI；业务规则和复杂状态转换放到可测试类型。
- 保持稳定 identity，列表使用稳定业务标识。
- 避免在 `body` 中执行 I/O、创建重型对象或触发副作用。
- 明确处理 loading、empty、error、permission denied 和 retry。
- 支持 Dynamic Type、VoiceOver、深浅色、安全区和常见设备尺寸。
- 使用语义 spacing/color/token；仅在设计尚未稳定时允许小范围局部常量。

## 错误处理与日志

- 不静默吞掉用户可见或影响状态一致性的错误。
- `try?` 仅用于失败确实等价于可接受缺省值的场景，并通过命名或注释说明。
- 日志不得包含凭据、用户输入原文或其他敏感信息。
- 面向用户的错误提供恢复动作；内部错误保留足够诊断上下文。

## 文档与注释

- 注释解释“为什么”、约束或非显然取舍，不复述代码。
- 公共 API 在契约不显然时添加 `///`。
- 新 Swift 文件使用 Xcode 生成的标准文件头并保持项目名为 `PauseGuard`。
- `TODO` 必须说明完成条件；长期事项应进入 issue 或技术债记录。

## 测试友好性

- 时间、随机、网络、存储和系统权限通过窄接口形成可替换测试边界。
- 测试行为而不是私有实现步骤。
- 修复回归时优先添加能在旧实现失败的测试。
